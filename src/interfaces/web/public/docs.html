SUBARU v1.0.0

Complete technical documentation for Subaru, a fully local AI assistant agent with autonomous tool use, multi-interface support, and an extensible plugin system.

What is Subaru?

Subaru is an autonomous AI agent that runs entirely on your local machine. It connects to a large language model (LLM) — either a local model via Ollama, or a cloud API like OpenAI or Anthropic — and gives the LLM direct access to your filesystem, shell, browser, database, git, and more through a powerful tool-calling system.

Unlike simple chatbot wrappers, Subaru operates as a true agent: it plans complex tasks, executes multi-step tool chains autonomously, stores memories across sessions, and provides three separate interfaces (CLI, Web, Telegram) for interacting with it.

Key Features

  • 36 built-in tools across 8 modules: filesystem, shell, HTTP, code execution, database, git, browser automation, and display
  • Autonomous agent loop with automatic multi-step tool chaining (up to 25 iterations per task)
  • Task planning for complex requests — automatically decomposes them into actionable steps
  • Dual memory system — short-term conversation history (with SQLite persistence) + long-term vector memory with semantic recall
  • Three interfaces — terminal CLI, web dashboard with SSE streaming, and Telegram bot
  • Plugin system — extend with custom tools by dropping .js files into plugins/
  • Safety layer — path/command blocking, confirmation prompts for dangerous operations, optional sandboxing
  • Multi-provider LLM support — Ollama (local), OpenAI, Anthropic with automatic retry and exponential backoff

Architecture

Subaru follows a modular architecture with clear separation of concerns. The system is built around a central agent loop that orchestrates communication between the LLM, tools, and memory systems.

┌─────────────────────────────────────────────────────────────────┐ │ INTERFACES │ │ CLI (readline) Web (Express+SSE) Telegram (Bot) │ └──────────────┬──────────────┬──────────────────┬───────────────┘ │ │ │ └──────────────┼──────────────────┘ ▼ ┌──────────────────────────┐ │ AGENT CORE │ │ Planner → Reasoner → Executor │ │ (multi-turn loop) │ └──────┬───────────┬────────┘ │ │ ┌─────────┘ └──────────┐ ▼ ▼ ┌──────────────────┐ ┌───────────────────────┐ │ LLM CLIENT │ │ TOOL REGISTRY │ │ Ollama│OpenAI│Anthropic│ │ 36 built-in + plugins │ │ Streaming + Retry │ │ Dispatch + Validation │ └──────────────────┘ └───────────────────────┘ │ │ ▼ ▼ ┌──────────────────┐ ┌───────────────────────┐ │ MEMORY │ │ SAFETY │ │ Short│Long│Prefs │ │ Permissions│Confirm│Sandbox│ └──────────────────┘ └───────────────────────┘

Every component communicates through well-defined interfaces. The agent doesn't call tools directly — it tells the LLM what tools are available; the LLM decides which to call; the executor validates and runs them; and results feed back into the conversation.

Getting Started

Prerequisites

  • Node.js 20+ (uses ESM imports, modern features)
  • Ollama (recommended, for local LLM) — or an OpenAI/Anthropic API key

Installation

# Clone and install
git clone <repo-url> autonome
cd autonome
npm install

# (Optional) Install globally via npm link
npm link

# Configure
cp .env.example .env
# Edit .env with your API keys and settings

# Start
npm start
# Or if linked globally:
autonome

Configuration Priority

Configuration is loaded in this order (later values override earlier):

  1. src/config/defaults.js — built-in defaults
  2. autonome.config.json — project-level configuration file
  3. .env file — environment variable overrides for sensitive values

Boot Sequence

When Subaru starts (src/index.js), it follows this exact initialization order:

  1. Load configuration — config/config.js reads defaults → merges autonome.config.json → applies .env overrides → freezes the config object
  2. Initialize logger — configured via LOG_LEVEL env var (debug/info/warn/error)
  3. Initialize preferences DB — opens SQLite at data/memory.db, creates preferences table
  4. Initialize conversation persistence — creates conversation_history table in same DB
  5. Initialize LLM client — imports the configured provider (Ollama/OpenAI/Anthropic)
  6. Initialize long-term memory — loads data/vectors/memories.json, probes embedding model availability
  7. Load tool registry — registers all enabled built-in tools, then scans plugins/ directory
  8. Start interfaces concurrently — launches Web server, CLI REPL, and/or Telegram bot based on config
  9. Register graceful shutdown — SIGINT/SIGTERM handlers cleanly close all resources

Agent Loop

The agent loop (agent/agent.js → run()) is the brain of Subaru. When a user sends a message, the entire agentic cycle runs:

User Message │ ▼ 1. Load short-term history (from session) │ ▼ 2. Recall long-term memories (vector similarity search, top-3) │ ▼ 3. Plan (if complex) (decomposes into numbered steps) │ ▼ 4. Build system prompt (tool descriptions + memories + plan) │ ▼ 5. Assemble messages[] (system + history + user message) │ ▼ ┌─── AGENT LOOP (max 25 iterations) ───┐ │ │ │ 6. Reasoner.think() │ │ → streams tokens to interface │ │ → collects tool_call events │ │ │ │ 7. If tool calls exist: │ │ → Executor validates + dispatches │ │ → Results appended to messages[] │ │ → LOOP BACK to step 6 │ │ │ │ 8. If no tool calls (text response): │ │ → EXIT LOOP │ │ │ └────────────────────────────────────────┘ │ ▼ 9. Save to short-term memory │ ▼ 10. Store in long-term memory (if significant) │ ▼ Response delivered to user

Planner

The planner (agent/planner.js) examines the user's message for complexity triggers — keywords like "create", "build", "deploy", "refactor", etc. or messages over 200 characters. If triggered, it makes a separate LLM call to generate a numbered step-by-step plan, which gets injected into the system prompt for the main agent loop.

Reasoner

The reasoner (agent/reasoner.js) is a thin async-generator wrapper around the LLM client. It calls llmClient.chat() with the current messages and tool definitions, yielding events as they stream in. This separation keeps the agent loop clean.

Executor

The executor (agent/executor.js) receives tool call requests from the LLM's response. For each call it:

  1. Looks up the tool in the registry
  2. Validates the input against the tool's JSON Schema using Ajv
  3. Calls the tool's execute() function with the input and a context object
  4. Returns the result formatted as a tool message for the LLM conversation

Tool results are truncated to 12,000 characters to prevent oversized messages from breaking the LLM API.

LLM Client

The LLM client (llm/client.js) provides a unified async generator interface across all providers. It handles:

  • Provider abstraction — dynamically imports the correct provider at startup
  • Retry logic — up to 3 retries with exponential backoff (2s, 4s, 8s) on transient failures
  • Streaming — all providers implement the same async generator protocol, yielding {type: "token"}, {type: "tool_call"}, and {type: "done"} events
  • Embeddings — unified embed(text) function for long-term memory. Falls back gracefully if unavailable

LLM Providers

Ollama (Local)

Default provider. Connects to a locally running Ollama instance at http://localhost:11434. Uses the /api/chat endpoint with streaming. Tool calls are handled via Ollama's native tool-calling support. For embeddings, it auto-tries nomic-embed-text, all-minilm, mxbai-embed-large models.

OpenAI

Uses the official openai npm package. Supports GPT-4, GPT-4o, etc. with native function calling and streaming. Requires LLM_API_KEY. Compatible with any OpenAI-compatible API (e.g. LM Studio, vLLM) by setting LLM_BASE_URL.

Anthropic

Uses the @anthropic-ai/sdk package. Maps OpenAI-format tool definitions to Anthropic's tool format. Handles Anthropic's unique streaming event protocol (content_block_start, content_block_delta, etc.).

Short-term Memory

Short-term memory (memory/shortTerm.js) manages per-session conversation history. Each interface maintains its own session ID (e.g., cli_main, web_abc123, tg_user_12345).

  • In-memory primary storage — Map<sessionId, message[]> for fast access
  • SQLite persistence — messages are also written to conversation_history table, enabling session restoration across restarts
  • Auto-trimming — when a session exceeds shortTermMaxMessages (default: 100), oldest non-system messages are dropped
  • Session management — supports listing all sessions, clearing per session, and loading from DB on first access

Messages stored include: role, content, timestamp, and optionally tool_call_id, name, tool_calls for tool interaction messages.

Long-term Memory

Long-term memory (memory/longTerm.js) provides semantic recall across sessions using vector embeddings.

How it works

  1. Store — when the agent completes a significant interaction, the text is embedded into a vector using the LLM's embedding model, then stored with metadata in data/vectors/memories.json
  2. Recall — when a new message comes in, it's embedded and compared to all stored memories using cosine similarity. Top-K results above the threshold are injected into the system prompt

Fallback Mode

If embedding models are unavailable (e.g., Ollama doesn't have an embedding model pulled), the system automatically falls back to a bag-of-words hash-trick approach:

  • Text is tokenized into words, each hashed to a bucket in a fixed 256-dimensional vector
  • Cosine similarity still works, but with keyword-level matching instead of semantic understanding
  • This ensures long-term memory always functions, even without embedding models

Preferences DB

The preferences system (memory/preferences.js) is a simple key-value store backed by SQLite. It stores user preferences that the agent learns over time (e.g., coding style, preferred languages). Preferences are injected into the system prompt automatically.

API: get(key), set(key, value), getAll(), del(key). Values are JSON-serialized.

Tool Registry

The tool registry (tools/registry.js) is the central hub for all tool management. It maintains a Map<name, toolObject> and handles:

  • Registration — registerTool(tool) / registerTools(array)
  • Lookup — getTool(name) / getAllTools()
  • Dispatch — dispatch(name, input, context) wraps execution with error handling
  • Loading — loadTools(config) imports each enabled module, then calls loadPlugins()
  • Plugin management — listPlugins(), savePlugin(), deletePlugin(), reloadPlugins()

Tools are loaded conditionally based on config. Each tool module is only imported if config.tools.{key}.enabled !== false.

Tool Execution Flow

When the LLM decides to call a tool, here's the exact sequence:

  1. The LLM streams a response containing tool_call events (via the provider's function calling protocol)
  2. The reasoner yields these events to the agent loop
  3. After the LLM finishes its response, the agent loop collects all tool calls for this turn
  4. An assistant message with tool_calls is appended to the conversation history
  5. For each tool call, the executor:
    • Resolves the tool from the registry
    • Validates input against the tool's JSON Schema (using Ajv with coerceTypes: true)
    • Calls tool.execute(input, context)
    • Returns a role: "tool" message with the JSON result
  6. All tool result messages are appended to the conversation
  7. The loop sends the updated messages back to the LLM for another iteration
  8. This repeats until the LLM responds with only text (no tool calls) or the 25-iteration cap is hit

CLI Interface

The CLI (interfaces/cli.js) provides a readline-based REPL in the terminal. It registers a confirmation handler for interactive command approval. Streamed tokens are printed to stdout in real-time. The CLI session uses the session ID cli_main.

Web Dashboard

The web interface is an Express server (interfaces/web/server.js) serving a single-page application (public/index.html) with:

  • Authentication — optional cookie-based auth (set WEB_AUTH_PASSWORD to enable)
  • Rate limiting — 30 POST requests per minute per IP on /api/chat
  • SSE streaming — chat responses stream via /api/stream/:taskId as Server-Sent Events
  • Collapsible sidebar — System info, Tools, Plugins, and Memory sections with persist-to-localStorage toggle states
  • Plugin management GUI — create, edit, delete plugins from the browser

Chat Flow

  1. Client POSTs to /api/chat with { message, sessionId }
  2. Server creates a task with an EventEmitter, starts the agent asynchronously
  3. Server returns { taskId, sessionId }
  4. Client connects to /api/stream/:taskId via EventSource
  5. Agent events (tokens, tool calls, results) are pushed as SSE data frames
  6. When done, a stream_end event closes the stream

Telegram Bot

The Telegram interface (interfaces/telegram/bot.js + handler.js) uses the node-telegram-bot-api package in polling mode. It supports:

  • Text messages and voice messages (via STT transcription)
  • Per-user sessions (tg_user_{userId})
  • Inline keyboard confirmations for dangerous operations
  • /clear command to reset conversation history

Permissions

The permissions module (safety/permissions.js) provides two checking functions:

Path Checking

checkPath(filePath, config) verifies a file path is allowed:

  1. Resolves ~ to home directory and normalizes the path
  2. Checks against blockedPaths — if the path starts with any blocked prefix, it's denied
  3. Checks against allowedPaths — if configured, the path must be inside at least one allowed directory
  4. Returns { allowed: boolean, reason: string }

Command Checking

checkCommand(command, config) checks for blocked command patterns (substring match against blockedCommands config array).

Confirmations

The confirmation system (safety/confirmation.js) provides per-interface confirmation prompts for dangerous operations:

  • CLI: Uses readline to prompt [CONFIRM] description (y/n): with a 30-second timeout
  • Web: Creates a pending confirmation stored in memory. The web client polls /api/confirmations and POSTs approval to /api/confirm/:confirmationId
  • Telegram: Uses inline keyboard buttons for approve/deny

All confirmation handlers return a Promise that resolves to true (approved) or false (denied/timeout).

Sandboxing

When safety.sandboxShell is enabled, shell commands are executed in an isolated environment (safety/sandbox.js):

  1. Firejail (preferred) — uses firejail --quiet --noprofile --net=none to run commands with no network access
  2. Docker (fallback) — runs commands in a node:20-alpine container with --network none
  3. Unsandboxed (last resort) — if neither is available, falls back to normal execution with a warning

Plugin Development Overview

Subaru's plugin system lets you extend the agent with custom tools by placing JavaScript files in the plugins/ directory. Plugins are loaded at startup and can also be managed at runtime through the web dashboard's Plugin Manager or the REST API.

When a plugin is loaded, its tools become available to the LLM just like built-in tools. The LLM sees the tool's name, description, and parameter schema, and can decide to call it autonomously when relevant to the user's task.

Key Concept

A plugin is simply a .js file that default-exports one tool or an array of tools. Each tool is a plain JavaScript object with a specific shape. No framework, no decorators, no build step.

Plugin Anatomy

A tool object has this exact structure:

{
  name: 'tool_name',              // Unique identifier (snake_case)
  description: 'What the tool does',  // LLM reads this to decide when to use it
  parameters: {                      // JSON Schema for input validation
    type: 'object',
    properties: { ... },
    required: [ ... ]
  },
  execute: async (input, context) => {  // The function that runs
    // Your logic here
    return { success: true, output: 'result' };
  }
}

Field Details

FieldTypeRequiredDescription
namestringYesUnique tool name. Use snake_case. This is what the LLM uses to invoke the tool. Must be unique across all tools (built-in and plugins). Examples: weather_lookup, translate_text, send_email
descriptionstringYesNatural language description of what the tool does, when to use it, and what it returns. This is the most important field — the LLM reads this to decide whether to call the tool. Be specific and descriptive. Include examples of when to use it.
parametersobjectYesJSON Schema object defining the expected input. Must have type: "object", properties: {}, and required: []. The executor validates input against this schema before calling execute.
executeasync functionYesThe function that actually performs the work. Receives (input, context). Must return a result object (see below).

Parameter Schema

The parameters field uses JSON Schema (validated by Ajv). This defines what inputs the LLM must provide when calling the tool.

parameters: {
  type: 'object',
  properties: {
    query: {
      type: 'string',
      description: 'The search query to look up'
    },
    limit: {
      type: 'number',
      description: 'Maximum number of results (default: 10)',
      default: 10
    },
    format: {
      type: 'string',
      enum: ['json', 'text', 'markdown'],
      description: 'Output format'
    },
    tags: {
      type: 'array',
      items: { type: 'string' },
      description: 'Optional filter tags'
    }
  },
  required: ['query']
}

Supported Types

TypeJSON SchemaNotes
String{ type: "string" }Supports enum for fixed choices, minLength, maxLength, pattern
Number{ type: "number" }Supports minimum, maximum, default
Integer{ type: "integer" }Same as number, integers only
Boolean{ type: "boolean" }true/false
Array{ type: "array", items: {...} }Define item type with items sub-schema
Object{ type: "object", properties: {...} }Nested objects for complex inputs
Important

Always add description to every property. The LLM uses these descriptions to understand what values to provide. Without descriptions, the LLM may pass incorrect or missing values.

Execute Function

The execute function is where your tool's logic lives. It receives two arguments:

execute: async (input, context) => {
  // input = validated object matching your parameters schema
  // context = runtime context (see next section)

  try {
    // Do work...
    const result = await someOperation(input.query);

    // Return success
    return {
      success: true,
      output: `Found ${result.count} items:\n${result.data}`
    };
  } catch (err) {
    // Return failure
    return {
      success: false,
      output: '',
      error: err.message
    };
  }
}

Return Object

FieldTypeDescription
successbooleantrue if the operation completed successfully, false on error
outputstringThe result text that gets sent back to the LLM. Make this human-readable — the LLM interprets it and presents it to the user. For structured data, use formatted text or JSON strings.
errorstring (optional)Error message when success: false. The LLM uses this to diagnose and potentially retry.
Tip

The output string is what the LLM "sees". Format it for the LLM, not the user. The LLM will then interpret and present it conversationally. Include relevant data in the output — don't be afraid of detail, but the executor will truncate outputs over 12,000 characters.

Context Object

The second argument to execute is a context object containing runtime utilities:

context = {
  config,          // The frozen config object (llm, tools, memory settings, etc.)
  logger,          // Logger instance with .debug(), .info(), .warn(), .error()
  confirmationFn, // async (description) => boolean — ask user for confirmation
  sessionId       // Current session ID (e.g., "web_abc123", "cli_main")
}
PropertyTypeDescription
context.configObjectThe full (frozen) Subaru config. Access tool settings, LLM config, memory settings. E.g., context.config.tools.shell.timeout
context.loggerLoggerStructured logger. Use context.logger.info('Processing...') for operational logging. Supports .debug(), .info(), .warn(), .error()
context.confirmationFnasync FunctionPrompt the user for "yes/no" confirmation before performing a dangerous action. Pass a description string; returns true if approved, false if denied or timed out (30s).
context.sessionIdstringThe caller's session ID. Useful for session-scoped state or per-user behavior.

Plugin Examples

Example 1: Simple Utility Tool

A tool that converts units:

// plugins/unit-converter.js

const conversions = {
  km_to_miles: v => v * 0.621371,
  miles_to_km: v => v * 1.60934,
  c_to_f: v => (v * 9/5) + 32,
  f_to_c: v => (v - 32) * 5/9,
  kg_to_lbs: v => v * 2.20462,
  lbs_to_kg: v => v * 0.453592,
};

export default [
  {
    name: 'convert_unit',
    description: 'Convert a value between common units. Supports: km↔miles, celsius↔fahrenheit, kg↔lbs. Use this whenever the user asks to convert between these units.',
    parameters: {
      type: 'object',
      properties: {
        value: { type: 'number', description: 'The numeric value to convert' },
        conversion: {
          type: 'string',
          enum: Object.keys(conversions),
          description: 'The conversion to apply'
        }
      },
      required: ['value', 'conversion']
    },
    execute: async ({ value, conversion }) => {
      const fn = conversions[conversion];
      if (!fn) {
        return { success: false, output: '', error: `Unknown conversion: ${conversion}` };
      }
      const result = fn(value);
      return {
        success: true,
        output: `${value} ${conversion.replace('_to_', ' → ')} = ${result.toFixed(4)}`
      };
    }
  }
];

        city: {
          type: 'string',
          description: 'City name (e.g., "Tokyo", "New York", "London")'
        }
      },
      required: ['city']
    },
    execute: async ({ city }, context) => {
      try {
        context.logger.info(`Fetching weather for: ${city}`);

        const resp = await fetch(
          `https://wttr.in/${encodeURIComponent(city)}?format=j1`
        );

        if (!resp.ok) throw new Error(`API returned ${resp.status}`);

        const data = await resp.json();
        const current = data.current_condition[0];

        return {
          success: true,
          output: [
            `Weather for ${city}:`,
            `  Temperature: ${current.temp_C}°C (${current.temp_F}°F)`,
            `  Feels like: ${current.FeelsLikeC}°C`,
            `  Conditions: ${current.weatherDesc[0].value}`,
            `  Humidity: ${current.humidity}%`,
            `  Wind: ${current.windspeedKmph} km/h ${current.winddir16Point}`,
          ].join('\n')
        };
      } catch (err) {
        return { success: false, output: '', error: `Weather lookup failed: ${err.message}` };
      }
    }
  }
];

Example 3: Tool with Confirmation

A tool that performs a dangerous action and asks for user confirmation:

// plugins/cleanup.js
import fs from 'node:fs';
import path from 'node:path';

export default [
  {
    name: 'cleanup_temp_files',
    description: 'Delete all temporary files older than N days from a specified directory. Asks for user confirmation before deleting. Use when the user wants to clean up old temp files.',
    parameters: {
      type: 'object',
      properties: {
        directory: { type: 'string', description: 'The directory to clean' },
        days: { type: 'number', description: 'Delete files older than this many days', default: 7 }
      },
      required: ['directory']
    },
    execute: async ({ directory, days = 7 }, context) => {
      const files = fs.readdirSync(directory);
      const cutoff = Date.now() - (days * 86400000);
      const oldFiles = files.filter(f => {
        const stat = fs.statSync(path.join(directory, f));
        return stat.mtime.getTime() < cutoff;
      });

      if (oldFiles.length === 0) {
        return { success: true, output: 'No files older than ${days} days found.' };
      }

      // Ask for confirmation before deleting
      const approved = await context.confirmationFn(
        `Delete ${oldFiles.length} files older than ${days} days from ${directory}?`
      );

      if (!approved) {
        return { success: true, output: 'Operation cancelled by user.' };
      }

      let deleted = 0;
      for (const f of oldFiles) {
        fs.unlinkSync(path.join(directory, f));
        deleted++;
      }

      return { success: true, output: `Deleted ${deleted} files.` };
    }
  }
];

Plugin Best Practices

Naming

  • Use snake_case for tool names: get_weather, send_email
  • Prefix related tools with a common namespace: slack_send, slack_read, slack_list_channels
  • Avoid generic names that conflict with built-in tools

Descriptions

  • Write descriptions as if explaining to a human assistant when to use this tool
  • Include what it does, when to use it, and what it returns
  • Mention specific use cases: "Use this when the user asks about weather"
  • The better your description, the more accurately the LLM will use the tool

Error Handling

  • Always wrap execute logic in try/catch
  • Return { success: false, error: "descriptive message" } on failure
  • The LLM reads error messages and may retry with different input or report the issue to the user
  • Don't throw unhandled exceptions — they'll be caught by the executor, but with less control

Performance

  • Keep tool execution fast. Long-running operations block the agent loop
  • For API calls, use timeouts (the agent has a 25-iteration budget)
  • Return concise but complete output — excessively large outputs get truncated at 12KB

Security

  • Use context.confirmationFn for destructive operations (deletes, sends, posts)
  • Validate inputs beyond what JSON Schema catches (e.g., URL format, path traversal)
  • Don't hardcode secrets — read them from environment variables or config
  • Be careful with user-controlled input in shell commands or file paths

SSE Event Types

The /api/stream/:taskId endpoint sends Server-Sent Events with the following JSON payload types:

TypeFieldsDescription
token{ type, content }A text token from the LLM response. Accumulate these for the full response.
tool_call{ type, tool, input }The LLM is calling a tool. tool is the tool name, input is the arguments object.
tool_result{ type, tool, output, success }A tool has returned a result.
done{ type, response? }The agent has finished processing. response may contain the full text if no tokens were streamed.
error{ type, message }An error occurred during processing.
stream_end{ type }The SSE stream is closing. Close your EventSource.
Client Example
const es = new EventSource('/api/stream/' + taskId);
es.onmessage = (event) => {
  const data = JSON.parse(event.data);
  if (data.type === 'token') appendText(data.content);
  if (data.type === 'stream_end') es.close();
};
